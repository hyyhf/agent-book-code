## Part 1: 先跑起来

先别急着理解 Agent。先把它用起来。

我见过很多学生卡在第一步。不是因为 Agent 难。而是界面、模型、工作区、权限混在一起，一下子搞不清楚从哪看。

这一部分只解决一件事：让 FunHarness Studio 正常工作。

---

## §01 打开 Studio 之后，先看这 3 个地方

结论先说。

打开 Studio 后，先看 3 个地方：左侧导航、中间对话区、右侧工作区。

![截图占位：FunHarness Studio 主界面](images/studio_manual/01-home.png)

### 01.1 左侧导航

左侧是你的入口。从上到下，大概是这条线：

| 入口 | 用来做什么 |
| --- | --- |
| 主页 | 回到对话区 |
| 新会话 | 开一个干净上下文 |
| 历史 | 查看本地会话记录 |
| Agents | 创建队友、拆任务、跑后台 |
| Agent Teams | 看团队协作可视化 |
| Agent Swarm | 看 DAG 协作流程 |
| 群聊 | 多智能体群组对话 |
| 运行面板 | 看任务、日志、计划 |
| 技能库 | 查看和管理 Skills |
| 记忆 | 查看和保存长期记忆 |
| 宠物 | 管理桌面宠物 |
| 设置 | 配工作区、模型、机器人、搜索 |

第一次只点 4 个就够：主页、设置、运行面板、历史。其他入口等跑通一次再看。

### 01.2 中间对话区

中间是主战场。你在这里输入需求，Agent 在这里回复，工具调用也出现在这里。

如果只想完成一个任务，多数时间待在主页就够。

### 01.3 右侧工作区

右侧是文件区。你可以看当前工作区文件，也可以打开文件预览。

这对教学很有用。学生能看到 Agent 真的在读写本地文件，不是只在聊天框里说话。

> **核心建议**：第一次打开时，不要乱切所有面板。先确认左侧、对话区、工作区这 3 块能看懂。

认识完界面，下一章开始配置工作区。

---

## §02 工作区先配对，不然后面都容易乱

我最先检查工作区。原因很简单：Agent 会读写文件，它必须知道在哪里动手。

![截图占位：设置 - 工作区](images/studio_manual/02-settings-workspace.png)

### 02.1 进入工作区设置

点击左侧 `设置`，默认进入 `工作区` 标签。这里有 3 个关键信息：当前运行工作区、工作区路径、默认路径。

只是体验，可以用默认路径。在课堂做实验，我建议每个学生选自己的实验目录：

```text
D:\funharness-labs\student-01
```

或者：

```text
E:\agent-course\lab01
```

### 02.2 选择目录

点击 `选择目录`，选一个干净文件夹，再点 `保存`。

保存后，看 `当前运行工作区` 是否变化。变了，就说明后端已经切过去。

### 02.3 打开目录

点击 `打开目录`，系统文件管理器会打开这个路径。

这一步看似多余，其实很重要。你要知道 Agent 改的是哪个地方。不要让学生在桌面、下载目录、项目目录之间来回猜。

### 02.4 什么时候恢复默认

只是临时试验，可以点 `恢复默认`，Studio 会切回默认工作区。

课堂上我建议少用这个按钮。默认目录容易混入旧文件。实验课要干净，工作区越干净，问题越少。

> **注意**：如果在浏览器预览版里打开 Studio，选择目录这类 Electron 能力可能不可用。桌面版体验更完整。

工作区搞定后，下一步配模型。

## §03 模型配置别省，这一步决定能不能回复

结论先说：没有模型配置，Studio 只是空壳。它能打开，但 Agent 不能真正工作。

![截图占位：设置 - 模型](images/studio_manual/03-settings-model.png)

### 03.1 进入模型设置

点击左侧 `设置`，再点 `模型`。这里可以看到模型配置列表。一般会有一个环境变量配置，也可以新增用户配置。

### 03.2 新增模型

点击新增，填 4 个字段：

| 字段 | 怎么填 |
| --- | --- |
| 名称 | 自己能看懂即可，比如 `DeepSeek`、`OpenAI` |
| Base URL | OpenAI-compatible 服务地址 |
| API Key | 服务商密钥 |
| Model | 模型名称 |

填完先点测试。测试通过，再保存。最后选为当前会话使用。

### 03.3 推荐课堂做法

教师演示时，我建议统一模型。学生跟练时，把模型配置截图放到课程资料里。

不要让每个学生自由猜字段。这会浪费一节课。

### 03.4 模型切换的影响

模型切换只影响后续会话。同一个问题换模型，结果可能不同。这不是 Studio 的问题，这是模型能力差异。

所以做实验报告时，要写清楚模型名称。

> **核心建议**：第一次上课，先准备一个可用模型配置。不要把模型申请、Key 管理和 Studio 操作混在同一节课里。

模型能连上后，开始第一次对话。

## §04 第一条消息，让 Agent 做一件小事

第一次不要让它做大项目。让它做一件能验证的事。

比如创建一个待办清单脚本。

![截图占位：第一次对话](images/studio_manual/04-first-chat.png)

### 04.1 推荐输入

直接输入：

```text
请在当前工作区创建一个 todo.py，支持 add、list、done 三个命令，并给我一个使用示例。
```

为什么选这个例子？因为它小，文件少，容易验证，学生能看懂。

### 04.2 看它怎么工作

发出消息后，看 3 类内容：第一，Agent 的自然语言回复。第二，工具调用卡片。第三，文件变化摘要。

如果它创建了文件，去右侧工作区找 `todo.py`，打开看看。

### 04.3 让它自己验证

接着输入：

```text
请运行一次最小验证，确认 add、list、done 都能工作。
```

这一步很关键。不要只看它写了什么，要看它是否验证。

Agent 产品的学习重点，就是过程，不是漂亮回答。

### 04.4 失败怎么办

如果它报错，不要立刻重开。继续输入：

```text
请根据错误信息修复，并重新验证。
```

失败本身就是教材。学生能看到：错误出现，错误被读取，方案被修改，验证再次执行。这比一次成功更有价值。

> **花叔的经验**：第一次教 Agent 工具调用时，我最怕学生只看最终答案。后来改成让他们盯工具卡片。理解速度明显快。

第一条消息跑通后，下一章看工具卡片。

## Part 2: 把它当学习工作台

Studio 的重点不是聊天。而是把 Agent 的过程露出来。

你要看见它如何调用工具，如何读文件，如何管理附件，如何使用技能。

这一部分开始进入"可观察使用"。

---

## §05 工具调用卡片，是理解 Agent 的第一扇窗

结论先说：工具卡片比最终回复更重要。

最终回复告诉你结果。工具卡片告诉你过程。

![截图占位：工具调用卡片](images/studio_manual/05-tool-card.png)

### 05.1 工具卡片里看什么

重点看 4 个东西：

| 内容 | 你要判断什么 |
| --- | --- |
| 工具名 | 它到底用了什么能力 |
| 参数 | 路径、命令、查询词是否正确 |
| 状态 | 是运行中、成功、失败，还是等待审批 |
| 输出 | 结果是否支持下一步判断 |

学生能看懂工具卡片，就开始理解 Agent Loop 了。

### 05.2 命令输出卡片

当 Agent 运行命令时，Studio 会显示命令输出。你要看退出状态，也要看最后几行。很多错误都在最后几行。

### 05.3 文件变化摘要

当 Agent 修改文件时，注意看文件变化摘要。可以让学生回答 3 个问题：它改了哪个文件，它为什么改，改完有没有验证。

回答不上来，说明还在"看热闹"，没有进入工程理解。

### 05.4 等待审批

如果权限模式需要审批，某些操作会停下来等你确认。这不是卡住，这是安全边界。

对于本地 Agent 来说，权限不是装饰，它是必须有的刹车。

> **核心建议**：课堂演示时，故意让 Agent 做一次读文件、一次写文件、一次运行命令。3 张卡片就能讲清楚工具调用。

工具看懂后，我们把材料交给 Agent。

---

## §06 附件和工作区文件，要分清楚

很多人第一次会混。附件是一回事，工作区文件是另一回事。

![截图占位：附件与工作区](images/studio_manual/06-attachments.png)

### 06.1 工作区文件是什么

工作区文件是目录里的真实文件。比如：

```text
todo.py
README.md
requirements.txt
```

Agent 可以读取，也可能修改。所以工作区适合放实验项目。

### 06.2 附件是什么

附件是当前会话临时加入的材料。比如：课程讲义、需求文档、表格、截图说明。

附件更像"这次对话的参考资料"，它不一定是项目文件。

### 06.3 什么时候用附件

适合用附件的场景：让 Agent 总结讲义，让 Agent 根据需求文档拆任务，让 Agent 检查作业说明，让 Agent 分析报告材料。

### 06.4 什么时候放工作区

适合放工作区的场景：要修改代码，要运行测试，要生成文件，要保留项目结果。

### 06.5 一个课堂练习

准备一个 `requirements.md`，上传为附件，然后输入：

```text
请根据附件里的需求，在工作区创建一个最小可运行版本，并列出你创建的文件。
```

学生会看到：附件提供需求，工作区承接产物，工具卡片显示过程。这 3 件事串起来，Agent 才真正变成工作台。

> **注意**：不要把敏感文件随便放进工作区或附件。Studio 是本地 GUI，但模型请求仍可能发送到你配置的模型服务。

材料入口讲清楚后，我们看 Skills。

## §07 Skills 面板，是给 Agent 换工作方法

我对 Skills 的理解很简单：它不是插件市场，它是工作方法库。

![截图占位：技能库](images/studio_manual/07-skills.png)

### 07.1 打开技能库

点击左侧 `技能库`，你会看到已安装 Skills。每个 Skill 通常有名称和描述，核心文件一般是 `SKILL.md`。

### 07.2 Skills 解决什么问题

同一个 Agent，做不同任务时，需要不同方法。写报告是一种方法，做代码审查是一种方法，写书又是另一种方法。

Skills 把这些方法放进独立文件，比把所有提示词写死更清楚。

### 07.3 怎么用一个 Skill

最简单的方式，在对话里明确说：

```text
请使用 xxx skill，帮我完成这个任务。
```

或者在支持的入口中选择技能。让 Agent 先读 Skill，再执行任务。

### 07.4 课堂怎么讲

我建议让学生打开一个 Skill，只看 3 件事：触发条件、工作流程、质量检查。

这 3 件事看懂了，学生就知道 Prompt 工程不是堆话术，而是把经验写成可复用流程。

### 07.5 一个练习

让学生写一个很小的 Skill，比如：

```text
当我说"检查作业"时，请按格式、运行结果、可读性三项给反馈。
```

然后放到 Skills 目录，再从 Studio 里查看。

> **核心建议**：初学者不要先学复杂插件。先学会读一个 `SKILL.md`。这一步更值钱。

有了 Skills，下一步是记忆。

## §08 记忆不是聊天记录，它是长期偏好

记忆要少写，但要写准。

![截图占位：记忆面板](images/studio_manual/08-memory.png)

### 08.1 打开记忆面板

点击左侧 `记忆`，这里可以查看已有记忆，也可以保存新记忆。

### 08.2 什么适合写进记忆

**适合写**：用户偏好、项目约定、课程规则、常用路径、团队命名习惯。

**不适合写**：一次性的中间结果、临时错误日志、没有复用价值的聊天内容。

### 08.3 好记忆示例

比如：

```text
本课程示例代码默认要求学生能在 Windows PowerShell 中运行。
```

再比如：

```text
用户偏好中文说明，代码注释保持简短，不要过度抽象。
```

这种记忆会影响后续工作，它有价值。

### 08.4 坏记忆示例

比如：

```text
刚才 todo.py 第 17 行报错。
```

这不适合长期保存。它只属于某次会话，放到记忆里反而污染上下文。

> **核心建议**：记忆像课程黑板上的长期规则。不要把草稿纸内容写上去。

记忆讲完，我们开始拆任务。

## Part 3: 让 Agent 开始协作

单个 Agent 能做事。多个 Agent 能分工。但分工不是越多越好。

你要知道什么时候用 Teams，什么时候用 Swarm，什么时候用群聊。

这一部分讲进阶使用。

## §09 Agents 面板：从一个任务开始拆

Agents 面板是命令工作台。它把常用 slash 命令做成表单。

![截图占位：Agents 面板](images/studio_manual/09-agents.png)

### 09.1 面板里有什么

Agents 面板有 5 个部分：团队、任务、后台、计划、命令手册。

它们对应的常用命令：

```text
/team
/delegate
/plan
/task
/tasks
/next
/done
/bg
/schedule
```

### 09.2 先用 /plan 拆任务

输入一个需求：

```text
做一个 todo.py 命令行工具，支持添加、列出、完成待办，并写一个最小测试。
```

点击执行，Studio 会生成 `/plan ...`，Agent 会拆出任务图。

### 09.3 查看任务

拆完后，切到任务列表，看每个任务的 ID、标题、状态、负责人、依赖关系。

这一步很适合教学。学生第一次看到：需求不是直接变代码，需求先变任务，任务再变执行。

### 09.4 用 /next 推进

点击 `/next`，Agent 会领取下一个 ready 任务。执行完后，用 `/done` 标记完成，如果生成了文件，写到完成产物里：

```text
/done T1 todo.py,tests/test_todo.py
```

### 09.5 后台运行

慢命令放后台：

```text
/bg run pytest -q
```

后台任务不会阻塞当前对话，稍后查看状态和输出即可。

### 09.6 定时计划

定时计划适合提醒或周期检查：

```text
/schedule create review in 10m 检查测试结果和队友反馈
```

到点后，它会触发一个 prompt，结果进入运行记录。

> **花叔的经验**：我讲任务系统时，最有效的演示是 `/plan`、`/next`、`/done` 三连。学生一下就明白"任务推进"不是玄学。

有了任务，再创建队友。

## §10 Agent Teams：适合 Leader 带队友

Agent Teams 适合一类场景：一个主 Agent 做 Leader，几个长期队友负责不同视角。

![截图占位：Agent Teams 面板](images/studio_manual/10-agent-teams.png)

### 10.1 先创建队友

在 Agents 面板的团队区，创建一个队友：

```text
/team create reviewer code_reviewer 关注代码质量、边界条件和测试覆盖
```

再创建一个：

```text
/team create teacher teaching_assistant 关注学生是否容易理解
```

名字要短，角色要清楚，指令不要太长。

### 10.2 委派任务

选择队友，填写任务：

```text
检查 todo.py 是否适合初学者阅读，并指出 3 个可以改进的地方。
```

执行后，对应命令类似：

```text
/delegate teacher 检查 todo.py 是否适合初学者阅读，并指出 3 个可以改进的地方。
```

### 10.3 看 Agent Teams 可视化

点击左侧 `Agent Teams`，这里会展示团队运行过程。你可以看到：Leader、队友节点、任务连线、执行状态、消息流、产物。

### 10.4 什么时候用 Teams

**适合用 Teams**：代码审查、作业批改、教学辅助、文案润色、测试补充。

**不适合用 Teams**：只有 1 个简单问题，任务没有分工价值，你只想快速问答。

### 10.5 Teams 的课堂玩法

我建议教师准备 3 个固定角色：`reviewer`、`tester`、`teacher`。

每次学生提交一个小项目，让 3 个队友分别给反馈。学生对比 3 份意见，就能理解"多视角"。

> **核心建议**：Teams 不是为了显得高级。只有当角色视角不同，Teams 才有价值。

Teams 是 Leader 模式。下一章讲 Swarm。

## §11 Agent Swarm：适合 DAG 协作

Swarm 和 Teams 不一样。Teams 像 Leader 带队，Swarm 像任务图协作。

![截图占位：Agent Swarm 面板](images/studio_manual/11-swarm.png)

### 11.1 Swarm 看什么

打开 `Agent Swarm`，你会看到：协作模板、运行历史、DAG 任务图、节点状态、共享黑板、事件流。

### 11.2 选择模板

Studio 内置多种模板：研究团队、代码审查、产品发现、数据分析、辩论。

你选择模板，填入目标，点击启动。

### 11.3 看 DAG 节点

每个节点是一项任务。节点可能有的状态：`pending`、`in_progress`、`completed`、`failed`。

你要看依赖关系：谁先做，谁后做，谁等待上游结果。这就是 DAG 的价值。

### 11.4 看共享黑板

共享黑板是 Swarm 的关键。一个 Agent 发现的信息，会发布到黑板，其他 Agent 可以使用。

学生要理解：协作不是每个人各做各的，协作需要中间发现被共享。

### 11.5 什么时候用 Swarm

**适合用 Swarm**：研究型任务、多步骤分析、并行检查、需要汇总的交付。

**不适合用 Swarm**：只需要一个简短回答，任务无法拆成依赖图，你不关心过程。

### 11.6 一个练习

输入目标：

```text
分析一个学生作业项目，给出代码质量、测试覆盖、文档完整性三方面反馈。
```

让 Swarm 跑一次，观察 3 个问题：哪个节点先执行，哪些发现进入黑板，最后交付物如何汇总。

> **注意**：Swarm 更适合演示"协作结构"。不要用它替代所有对话。

Swarm 讲结构，群聊讲交互。

---

## §12 群聊：让多个智能体在一个房间里讨论

群聊面板适合讨论。它不是任务图，也不是简单委派，它更像一个小组会议。

![截图占位：群聊面板](images/studio_manual/12-groups.png)

### 12.1 群聊适合什么

**适合**：方案讨论、角色辩论、教学问答、多角色点评。

**不适合**：严格任务编排，需要确定依赖关系的流水线，需要后台长期执行的工作。

### 12.2 创建角色

你可以创建几个角色，比如：产品老师、代码助教、测试助教。然后让它们围绕一个问题讨论。

### 12.3 观察互动

群聊的重点是观察观点碰撞。你要看：谁提出问题，谁补充证据，谁给出反对意见，谁总结方案。

### 12.4 课堂玩法

把同一个项目交给群聊，让不同角色讨论：

```text
这个 todo.py 是否适合作为第 1 次编程作业？请从教学难度、代码质量、测试要求三个角度讨论。
```

然后让学生总结：哪些建议可以采纳，哪些建议过度了。

> **核心建议**：群聊面板适合训练判断力。不要把所有角色意见都当最终答案。

讨论结束后，要会复盘。

---

## §13 运行面板：看任务、日志和计划

运行面板是复盘入口。它不负责"说得漂亮"，它负责"查得清楚"。

![截图占位：运行面板](images/studio_manual/13-dashboard.png)

### 13.1 运行面板看什么

点击左侧 `运行面板`，你会看到：任务流水线、运行时任务、计划任务、快捷诊断。

### 13.2 任务流水线

这里看任务进度，重点看：任务状态、任务详情、验证标准、产物、错误信息。

如果一个任务卡住，先看详情，不要直接重新开始。

### 13.3 运行时任务

后台命令都在这里：测试、构建、长时间脚本。你可以点 `输出日志` 查看完整输出，也可以终止还在运行的任务。

### 13.4 计划任务

定时 prompt 会出现在这里，你可以看：触发规则、是否启用、上次运行、下次触发、关联 runtime。

### 13.5 快捷诊断

运行面板里有快捷诊断入口，包括：Cost Dashboard、Trace Timeline、Recent Logs、Failure Analysis。

这些按钮会发送对应命令：

```text
/trace
/logs
/dashboard
/failures
```

### 13.6 复盘模板

每次任务结束后，我建议学生写 5 行复盘：

```text
目标：
Agent 做了什么：
调用了哪些工具：
失败点：
下次怎么改 prompt：
```

这比只保存最终代码更重要。

> **花叔的经验**：学生真正进步，不是在 Agent 成功时，而是在他们能说清楚"为什么失败"时。

复盘还可以用历史回放。

## §14 历史和 Session 演绎：把一次会话重新看一遍

历史不是聊天收藏夹，它是实验记录。

![截图占位：历史与 Session 演绎](images/studio_manual/14-session-replay.png)

### 14.1 打开历史

点击左侧 `历史`，你会看到本地会话记录。选择一条，可以查看当时的对话。

### 14.2 Session 演绎看什么

Session 演绎会把一次会话组织成节点，常见节点包括：`system`、`user`、`reasoning`、`assistant`、`tool_call`、`tool_result`、`error`。

沿着节点看流程：谁触发了谁，哪个工具返回了什么，错误在哪里出现。

### 14.3 适合写实验报告

实验报告不要只贴最终结果。我建议加 3 张图：第一张，用户需求；第二张，关键工具调用；第三张，错误修复或最终验证。

Session 演绎可以帮你找这些节点。

### 14.4 什么时候开新会话

如果上下文乱了，开新会话。如果任务目标变了，开新会话。如果只是小修小补，留在当前会话。

新会话不是失败，它是清理上下文。

> **核心建议**：每个实验目标用一个会话。不要把 5 个不相关任务塞进同一条历史。

下一章讲一个小功能：宠物。

## §15 宠物面板：它不是核心，但很适合课堂气氛

宠物不是 Agent 能力的核心。但它有教学价值：它把状态变得可感知。

![截图占位：宠物面板](images/studio_manual/15-pets.png)

### 15.1 打开宠物

点击左侧 `宠物`，你可以管理桌面宠物，包括：是否显示、位置、大小、选择宠物、添加宠物。

### 15.2 宠物状态是什么意思

宠物会跟随 Agent 状态变化。比如：启动、思考、等待、运行、跳跃、审视、失败、挥手。

这对课堂演示很友好。学生不用读日志，也能感到 Agent 正在做事。

### 15.3 什么时候关闭

录正式课程或做严肃调试时可以关闭。它不影响核心功能。

### 15.4 自定义宠物

课程需要趣味化，可以上传自定义 Sprite Sheet。建议提前测试，不要在课堂现场调图片格式。

> **核心建议**：宠物适合调动注意力，不适合替代状态面板。真正排错还是看工具卡片和运行面板。

最后讲外部通道。

## §16 频道机器人：把同一个 Agent 接到飞书、QQ、微信

Studio 不只是一块屏幕，它还能配置外部聊天通道。

![截图占位：频道机器人设置](images/studio_manual/16-bots.png)

### 16.1 入口在哪里

点击 `设置`，再点 `频道机器人`。这里有 3 类通道：飞书、QQ Bot、微信。

### 16.2 飞书通道

飞书适合课堂组织。你需要准备：App ID、App Secret、权限模式。保存后启动。

学生可以在飞书里发消息，本地 FunHarness 负责执行。

### 16.3 QQ Bot

QQ Bot 适合已有 QQ 群的教学场景。你需要：App ID、Client Secret、权限模式。保存后启动。

### 16.4 微信通道

微信通道用扫码登录。第一次需要扫码，成功后会保存登录凭据，再启动通道。

### 16.5 权限模式怎么选

| 模式 | 适合场景 |
| --- | --- |
| auto | 本地可信工作区，演示流畅优先 |
| suggest | 希望有一定保护，不想每步都审批 |
| approve | 高风险演示，需要明确确认 |

课堂上我更偏向 `suggest`。演示更稳，也能讲清楚安全边界。

### 16.6 外部通道的边界

IM 通道适合收发消息，但不适合所有交互。比如复杂审批、文件路径选择、多面板观察，这些还是 Studio 更方便。

> **注意**：机器人通道会把聊天平台和本地 Agent 连起来。请只在受信任工作区中启用。

到这里，主要使用路径已经完整。

## Part 4: 常见工作流

前面是面板，现在是任务。

真正使用时，你不会按面板思考，你会按目标思考。这一部分给你几条常用路线。

---

## §17 工作流一：让 Studio 帮学生做一个小项目

目标：用 Studio 完成一个最小项目。

### 17.1 准备

选择干净工作区，确认模型可用，打开主页。

### 17.2 输入需求

```text
请帮我创建一个 Python 命令行小项目 todo.py，支持 add、list、done 三个命令。请写出最小测试，并运行验证。
```

### 17.3 观察过程

看工具卡片，看文件变化，看命令输出。

### 17.4 要求验证

如果它没主动验证，补一句：

```text
请运行测试或最小命令验证，并告诉我验证结果。
```

### 17.5 复盘

打开运行面板，看是否有后台任务。打开工作区，确认文件存在。打开历史，保存这次会话。

### 17.6 交付标准

学生最后要交 4 样东西：代码文件、验证输出、关键工具调用截图、一句失败或成功原因。

---

## §18 工作流二：把需求文档变成任务图

目标：从一份文档生成任务计划。

### 18.1 上传附件

上传 `requirements.md`，不要先让 Agent 写代码，先让它读需求。

### 18.2 生成任务

输入：

```text
请根据附件需求，拆成可执行任务图。每个任务要有标题、说明、验证标准和依赖关系。
```

或者在 Agents 面板用 `/plan`。

### 18.3 检查任务质量

看 4 个点：任务是否太大，依赖是否清楚，验证是否具体，是否遗漏输入输出。

### 18.4 再开始执行

确认任务后，再让 Agent 执行第一个 ready 任务。不要让它一口气做完。任务图的价值在于可控。

---

## §19 工作流三：让队友审查作业

目标：让多个角色审查学生代码。

### 19.1 创建队友

```text
/team create reviewer code_reviewer 关注代码质量、异常处理和测试覆盖
```

```text
/team create teacher teaching_assistant 关注是否适合初学者理解
```

```text
/team create tester test_engineer 关注边界条件和验证方式
```

### 19.2 分别委派

```text
/delegate reviewer 检查当前工作区的 todo.py，给出 3 条代码质量建议。
```

```text
/delegate teacher 检查当前实现是否适合作为学生作业示例。
```

```text
/delegate tester 设计 5 个最小测试场景，并指出当前是否覆盖。
```

### 19.3 汇总结果

回到主页，输入：

```text
请汇总三个队友反馈，分成必须修改、建议修改、可以忽略三类。
```

### 19.4 课堂讨论

让学生判断：哪些建议真的重要，哪些建议过度工程化，哪些建议适合下一版。

这一步训练判断力，不是训练服从模型。

---

## §20 工作流四：用 Swarm 做一次研究型任务

目标：让多个 Agent 按 DAG 完成一份交付。

### 20.1 选择模板

打开 Agent Swarm，选择研究或代码审查类模板。

### 20.2 输入目标

例如：

```text
分析 FunHarness Studio 是否适合作为 AI Agent 教学工作台，给出功能优点、学习门槛和课堂使用建议。
```

### 20.3 观察黑板

不要只等最终结果。看中间发现，看哪个节点发布了信息，看后续节点是否使用。

### 20.4 导出结论

最终让主 Agent 汇总：

```text
请根据 Swarm 运行结果，整理成一页课堂讲义。
```

### 20.5 复盘

回答 3 个问题：DAG 是否合理，黑板是否有价值，最终结果是否比单 Agent 更好。

如果答案是否定的，说明这个任务不适合 Swarm。这也是好结果。

## Part 5: 排错

软件不是魔法，Agent 更不是。它会失败，关键是你知道去哪看。

---

## §21 常见问题清单

先看这张表：

| 问题 | 先检查哪里 | 常见原因 |
| --- | --- | --- |
| Agent 不回复 | 设置 - 模型 | API Key、Base URL、模型名错误 |
| 文件没生成 | 工作区 | 选错目录，或权限不允许写入 |
| 命令一直跑 | 运行面板 | 后台任务未结束，命令卡住 |
| 看不到工具输出 | 工具卡片、运行日志 | 输出折叠，或后台任务未读取 |
| 队友没反应 | Agents、运行面板 | 委派进入后台，需看 runtime |
| Swarm 没启动 | Swarm 面板、模型配置 | 模板变量缺失，或模型调用失败 |
| 搜索失败 | 设置 - 搜索服务 | AnySearch 或 Tavily Key 未配置 |
| 机器人收不到消息 | 设置 - 频道机器人 | 凭证错误，通道未启动 |
| 微信无法启动 | 频道机器人 | 未扫码，凭据过期 |
| 会话太乱 | 新会话 | 上下文混入多个任务 |

### 21.1 我的排错顺序

第一，看模型。第二，看工作区。第三，看工具卡片。第四，看运行面板。第五，看日志。

这个顺序很省时间。不要一上来就怀疑代码，很多问题只是配置错了。

### 21.2 让 Agent 自己读错误

如果有错误输出，直接让 Agent 读：

```text
请根据刚才的错误输出判断原因，并给出最小修复步骤。
```

不要把问题描述成：

```text
坏了，帮我看看。
```

太模糊，Agent 也需要证据。

### 21.3 保留失败现场

不要马上清空会话，不要马上删文件。先截图，先保存日志，先写下复现步骤。

失败现场是最好的教材。

> **核心建议**：排错时只改一个变量。不要同时换模型、换目录、换 prompt、换任务。

## §22 教师课堂使用建议

我会把 Studio 当"投影友好"的 Agent 教具。不是让学生只点按钮，而是用界面建立直觉。

### 22.1 第一节课

只讲 4 件事：工作区、模型、对话、工具卡片。

不要讲 Swarm，不要讲机器人。第一节课信息太多，学生会散。

### 22.2 第二节课

讲任务系统。用 `/plan` 拆需求，用 `/next` 推进，用 `/done` 收尾。再用运行面板复盘。

### 22.3 第三节课

讲多 Agent。先 Teams，再 Swarm，最后群聊。顺序不能反。

Teams 最容易理解，Swarm 需要 DAG 直觉，群聊需要判断力。

### 22.4 作业建议

每次作业要求学生交：最终产物、关键工具调用截图、一次失败修复记录、一段反思。

不建议只交最终代码，那样看不到学习过程。

### 22.5 评分建议

可以按 4 项评分：目标是否清楚，过程是否可复盘，验证是否完成，是否能解释失败。

这比"代码是否一次生成成功"更合理。

## §23 学生自学建议

如果你是学生，我建议你按小任务练，不要上来就做大项目。

### 23.1 每天一个小实验

- **第 1 天**：让 Agent 创建 `todo.py`
- **第 2 天**：上传需求文档，让它拆任务
- **第 3 天**：创建一个 reviewer 队友
- **第 4 天**：跑一次 Swarm
- **第 5 天**：用历史回放写复盘

### 23.2 不要迷信一次成功

一次成功不代表你学会了。你要能解释：它为什么这么做，它调用了什么工具，它哪里可能错，你怎么验证。

### 23.3 你的提示词要具体

**差提示词**：

```text
帮我做个项目。
```

**好提示词**：

```text
请在当前工作区创建一个 Python CLI todo 项目，支持 add、list、done。先列计划，再创建文件，最后运行最小验证。
```

好提示词不是更长，是目标、范围、验证更清楚。

### 23.4 学会停下来

当 Agent 连续改错 2 次，停下来，让它总结当前状态：

```text
请不要继续改代码。先总结当前文件状态、已尝试方案、失败原因和下一步最小修复。
```

这句话很好用，它能把混乱拉回结构。

## 最后一页

FunHarness Studio 的价值，不是让你少学命令，也不是让 Agent 看起来更像产品。

它真正的价值，是把过程摆到你面前。

你能看见工具调用，能看见文件变化，能看见任务拆解，能看见后台运行，能看见团队协作。

这就是教学需要的东西。

先用起来。再复盘。再打开代码。

到那一步，你看到的就不是一个 GUI。而是一个可以拆、可以改、可以继续长大的本地 Agent 工作台。
